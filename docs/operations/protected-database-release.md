# Database releases from GitHub

An authorized maintainer can open **Actions → Approved database release → Run workflow** in a browser on a phone, tablet or computer. Select `main`, enter its full reviewed commit SHA and the previous verified LIVE SHA from Render. Ordinary releases and emergency forward fixes use the same path. NeoApps account sign-in and employee permissions are separate from GitHub release authority.

## One-time activation requires owner/DBA approval

1. On this public repository, protect main with an active repository ruleset requiring a reviewed PR, code-owner review and dismissal of stale approvals. Include all code because migrations import the application. Protect the ruleset, environment administrators and CODEOWNERS, restrict who can change them, and remove bypasses and force pushes. The owner chooses the trusted code owners and named release reviewers. Confirm an approved change can actually be reviewed under the chosen rules.
2. Pre-create three environments with custom deployment **branch** policy containing exactly `main`, no tags or other branches, and require named trusted user reviewers. Disallow administrator bypass. Give maintainers only the access their job requires. The workflow checks GitHub's actual branch and environment policy before requesting an environment. After approval it checks the approving user and environment ID on that specific manual run. A re-run needs a new dispatch. Inspect the GitHub deployment approval screen for this workflow and exact SHA before approving. Keep unrelated workflows out of privileged environments. Restrict administration of repository/organization secrets, deployment workflows and runner settings.
3. Follow the ownership, shared TEMP and restricted-role gates in the database cutover procedure. Enable migrations only after validating actual grants and external consumers. Store the dedicated direct Neon migration DSN **only** in environment `neoapps-migration` as `MIGRATION_DATABASE_URL`. Use a hostname-verified TLS connection (`sslmode=verify-full`, with the runner's trusted CA bundle via `sslrootcert`) and an explicit application schema search path. Pin nonsecret `RELEASE_DATABASE`, `RELEASE_SCHEMA`, `RELEASE_MIGRATOR`, `RELEASE_RUNTIME`, `RELEASE_STANDBY`, `BOOTSTRAP_ADMIN_USERNAME` and `BOOTSTRAP_ADMIN_EMAIL` as environment variables. The service-specific migration expects the existing bootstrap account and cannot create it. Do not supply an administrator password. Stop if the existing network policy cannot admit the hosted runner safely. A database-wide network opening is outside this design.
4. Store only the service-specific deploy hook in `neoapps-render-release` as `RENDER_DEPLOY_HOOK`, with the intended service ID in `RENDER_TARGET_SERVICE`. The `neoapps-live-verification` environment needs no secrets. Do not use organization/repository secrets for database or deployment credentials. Use only standard GitHub-hosted Ubuntu runners. The deployment job and Render service never receive the migration DSN. The migration job never receives the deploy hook or either restricted login password.
5. Before merging or changing credentials, coordinate the first release with the DBA and Render administrator. Turn automatic deployments off on the existing service for this gated sequence. Maintain the restricted runtime DSN and expected-identity pins on Render. Build normally, retain `python scripts/bootstrap_database.py` as pre-deploy, and start Gunicorn normally. On this candidate the hosted command verifies the receipt and effective privileges read-only. Avoid serving an older startup script with new credentials. Verify the web/worker environment, bindings and inherited secret sources privately. Retain a compatible restricted fallback outside the service. Configure no privileged DSN on Render.
6. Before enabling real secrets, commission the dispatch, approvals, denial on disallowed refs, and release sequence against disposable targets. A PR rehearsal proves runner and application behavior with generated credentials. It cannot certify the installed production environment, network access, credential custody, approvals or live database roles. Use existing resources only. No paid runner, new service or plan change is required.

## Execution and evidence

The preflight checks the current main revision, code review rule, environment branch restrictions and required reviewers. A secret-free disposable PostgreSQL rehearsal and a fresh-runner isolation check must pass. Approval releases the migration to a fresh VM. The runner installs reviewed Linux x86-64 CPython 3.12 wheel hashes, then invokes the existing clean-checkout migration command with only its required environment. Only the dedicated migration identity applies the schema and seals the exact SHA after both restricted policies verify. GitHub retains the initiating actor, SHA, approval, job outcome and same-run rollback rehearsal. Keep longer-lived sanitized release evidence with the change record. Bootstrap diagnostics can contain account information and stay out of public CI logs.

After migration, the Render release reviewer confirms the prior deployment remains healthy and the intended SHA is still current. A separate job sends a single SHA-pinned deploy request. A queued or ambiguous response requires inspecting Render history before taking further action. The workflow records a confirmed deployment ID. Render's pre-deploy gate refuses an incorrect login, missing receipt or policy drift. A deploy acceptance alone leaves the release unverified.

For the final approval, check the exact LIVE SHA and deployment ID in Render, inspect an authorized read-only screen and a restricted access outcome, and check existing worker logs and a naturally due durable receipt after connection replacement. Reconcile the pre-release operational/audit fingerprints, accounting for concurrent legitimate changes. Do not generate business writes or start off-hours polling. If any evidence is missing, leave the verification pending. After the checks pass, the reviewer records the following comment on the **live-verification** environment approval, substituting the observed full revision and deployment ID.

```text
LIVE <sha> <dep-id> AUTH PASS WORKERS PASS
```

The final job verifies the approving account and that comment and makes one read-only liveness request. Record the Run URL, deployment ID, health, authorization/worker evidence, previous LIVE SHA and any rollback action. Keep operational details and provider secrets private.

## Failure and rollback

A preflight failure or missing approval leaves migration unstarted. Migration failure withholds deployment. Some existing migrations commit in stages. Inspect effects privately and establish compatibility before another dispatch. A present receipt is not evidence of a successful deployment. A failed Render pre-deploy must leave the old healthy deployment serving. A post-deploy discrepancy requires stopping the release and following the restricted fallback procedure on a verified compatible build. Replacing credentials cannot undo schema or data changes or fix a shared grant defect. Never select an earlier environment snapshot containing the broad credential as a shortcut. Emergency releases use the same audited approvals from the service interface.

For dependency changes, resolve `requirements.txt` for Ubuntu x86-64 and CPython 3.12 in a clean environment, using pip's JSON report and PyPI wheels. Review the resolved versions, origins and SHA-256 hashes in `scripts/release/requirements-linux-py312.lock`; the rehearsal installs those exact wheels and checks dependency compatibility.

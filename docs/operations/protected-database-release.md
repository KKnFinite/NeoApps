# Single-owner database releases

The NeoApps owner can release from a signed-in GitHub browser on a phone, tablet or computer. Employee accounts and application permissions are separate from release authority.

## Run a release

1. Inspect the PR diff and the successful **Disposable database release rehearsal**. Check any new migration for compatibility with the application still serving traffic. Merge the PR as `KKnFinite` after the one-time activation steps below are complete.
2. Open **Actions → Approved database release → Run workflow** on `main`. Enter the full merge SHA and the previous LIVE SHA from Render. The workflow verifies the repository, the first-attempt dispatch, the initiating account and the exact PR merger against GitHub. It runs the rehearsal again against the two release revisions.
3. On the run's **Review deployments** screen, check the workflow, SHA and **neoapps-migration** environment. Enter `MIGRATE <full release SHA>` as the approval comment and approve. This is the explicit authorization for the dedicated migration job. Render's prior LIVE SHA, health, protected-route response, deploy policy and pre-deploy command must pass verification first. Successful migration seals an exact-SHA database receipt.
4. Review the migration outcome and confirm the old service is healthy. Approve **neoapps-render-release** on the same run. The job rechecks the prior deployment, sends one SHA-pinned deploy request and records Render's deployment ID. Inspect Render history before retrying an ambiguous request.
5. Verify a signed-in, authorized read, a denied access outcome, and a normally due worker receipt on the new deployment. Compare business and audit fingerprints while accounting for legitimate concurrent changes. Approve **neoapps-live-verification** with `LIVE <full release SHA> <deployment ID> AUTH PASS WORKERS PASS`. The job independently checks Render's ID and SHA, public health and the signed-out login redirect. Preserve the run URL and the private worker and authorization evidence. Missing evidence leaves this step pending.

GitHub records one owner's decisions. A compromised owner account can approve a release or change repository policy. This model provides no independent human review. Protect the owner's GitHub account with strong authentication and existing account recovery safeguards. A release retry requires a fresh manual dispatch and confirmations.

## One-time activation

These actions require separate production authorization. Prepare them while the existing service continues operating.

- **GitHub main.** Use an active ruleset requiring a PR and the `isolation` status check from the GitHub Actions app (ID `15368`). The check follows the disposable rehearsal. Block force pushes and branch deletion, disable bypasses, and restrict repository administration and merging to the owner. Use zero required PR approvals, with required code-owner review and last-push approval off. CODEOWNERS identifies the responsible owner. The release checks that the owner's immutable account ID merged the exact commit. Examine all changes to workflows, actions, dependencies and migration code before merging.
- **GitHub environments.** Pre-create `neoapps-migration`, `neoapps-render-release` and `neoapps-live-verification`. Each must have exactly one custom deployment branch, `main`, and no tags. Set the sole required reviewer to `KKnFinite` (ID `271867764`), turn **Prevent self-review** off, and disable administrator bypass. The workflow verifies the approval history for the specific run and environment. Check bypass settings in the dashboard if the API omits them.
- **Credential custody.** Put the dedicated direct Neon DSN only in the migration environment as `MIGRATION_DATABASE_URL`. Use hostname-verified TLS, an explicit schema search path and reviewed network access. Set `RELEASE_DATABASE`, `RELEASE_SCHEMA`, `RELEASE_MIGRATOR`, `RELEASE_RUNTIME`, `RELEASE_STANDBY`, `BOOTSTRAP_ADMIN_USERNAME` and `BOOTSTRAP_ADMIN_EMAIL` there. The release requires the existing bootstrap account and needs no administrator password. Put the service-specific `RENDER_DEPLOY_HOOK` only in the deploy environment. Each environment uses `RENDER_TARGET_SERVICE` and a metadata-only `RENDER_VERIFICATION_KEY` limited to reading service and deployment details. Use environment secrets for these credentials. GitHub environments restrict refs and approvals; they do not provide a workflow-filename allowlist. The required rehearsal checks all workflow files for access to these environment names and rejects dynamically selected environments and unaudited external reusable workflows. Approve only the expected workflow on the exact run.
- **Render first.** Before merging the release tooling or switching identities, turn **Auto-Deploy** off on the existing Starter service, check for queued deployments and record the current LIVE SHA. Prepare the restricted runtime and fallback under the [database cutover procedure](runtime-database-cutover.md). Verify that both the still-serving application and the fallback retain required grants before an ownership transfer. If continuity cannot be established, hold the transfer. Keep the migration DSN off Render, including its build settings, environment groups and secret files. Keep the service's `python scripts/bootstrap_database.py` pre-deploy command. On the candidate it verifies the restricted identity, schema and receipt without migrating. Coordinate first-time runtime credential replacement with the release so an old bootstrap cannot run with new credentials.
- **Provider commissioning.** Before supplying live credentials, run the installed dispatch on disposable targets with environment policies equivalent to production. Verify the owner's approval screen, rejection/cancellation, and secret separation. A hosted PR rehearsal exercises the gate, operating-system isolation and database workflow. It cannot attest to future production secrets or the settings of environments that have not been created. The design uses standard GitHub-hosted runners and the existing Render Starter service.

## Failure and rollback

If a release check fails, stop at that stage. If migration partially committed, inspect the database privately before a fresh dispatch. While a deploy is pending or rejected, the old application must keep serving against the migrated schema. The rehearsal signs in an employee using the previous checkout, saves before and after migration and after a rejected startup, then saves again over a fresh restricted fallback connection. It verifies audit fingerprints and durable worker recovery.

For an emergency release, use the same owner workflow on any device. A compatible forward revert can retain the read-only pre-deploy gate. For a connection failure use the previously tested restricted fallback, replace pools, and verify the receipt and worker progress. Reconnecting cannot undo schema changes or repair a grant defect shared by both logins. An old Render rollback can restore historical environment variables; never roll back to a configuration containing elevated credentials. Retain private evidence of any rollback.

For release dependency updates, resolve `requirements.txt` for Ubuntu x86-64 and CPython 3.12 in a clean environment. Review wheel sources, versions and SHA-256 hashes in `scripts/release/requirements-linux-py312.lock`. The release installs the pinned wheels and checks their dependencies.

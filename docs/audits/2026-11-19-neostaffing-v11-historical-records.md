Local review branch `design/neostaffing-v11` started from `a5ce5a2ffb9fc79e13f9c1d659269faba22b9bee`. Verification used isolated synthetic databases. Production coverage and workforce size were left unmeasured.

## Capture and reporting

- `staffing_roster_revisions` records a cutover baseline and the minimum fields used by the live roster. It records changes to employee identity, classification and active state, area name and hierarchy, and assignment membership. There are no notes, contact fields, pay details or Shift Flow fields. Changes and removals are recorded in the same PostgreSQL transaction as the original writes. No-op source changes create no history row.
- `staffing_roster_closes` is keyed by canonical Sort Date Operation. It retains the captured gateway, Sort definition, Sort date, UTC opening and closing boundaries and publication time. The existing worker visits the default Staffing gateway on its regular safety heartbeat. It looks back seven local days, enrolls known operations whose entire window is covered, and seals at most one due operation per pass. It uses the configured window observed at enrollment. For an operation first seen after its window was edited mid-Sort, the service leaves coverage unavailable. Ambiguous DST boundaries are likewise unavailable. Never interpret zero captured placements as a missing roster if an eligible empty Sort was actually sealed.
- The roster becomes final at the configured local Sort close, using successful roster changes whose last journaled mutation was strictly before that boundary. PostgreSQL does not supply commit timestamps here. A transaction whose actual database commit lands after close can still be attributed before close if all of its roster mutations occurred beforehand. A transaction recording mutations on both sides of the boundary is excluded in its entirety. The worker defers while a roster write transaction is open, so rolled-back changes cannot enter a sealed roster. Publication is atomic and may follow the boundary after the next safety tick or retry.
- `staffing_roster_placements` keeps employee identity and classification and the captured work-area path. It uses the operational attendance-roster population, including active non-management employees regardless of whether they have a mark. Later transfers and edits never rewrite it. Multiple legitimate FT Combo Sort placements are displayed in their own areas. The report deduplicates people in the assigned headcount. An attendance mark without a matching close placement remains attendance evidence only.
- `staffing_attendance_outcomes` retains the latest authorized recorded status per employee and operation, original area, employee identity, available classification, and recorded and updated timestamps. An explicit clear leaves a status-free row so an older source cannot reappear. Daily-detail rollover copies still-linked marks in the same transaction before deletion. The optional cutover import copies supported surviving timecard marks, with unknown classification where provenance is absent. No notes, work-hours segments or inferred HERE are stored. Existing corrections and attendance authorization still apply.
- Reports are read-only and use current authorized area scope intersected with the recorded work area. Named rows retain the existing manager/Master boundary. Employee History uses the captured name or ID where available and applies classification to the retained outcome. It shows the Sort next to the date so two Combo marks on one day remain distinct. Daily Staffing labels complete, partial and unavailable evidence. Older timecards and daily detail remain usable within existing retention if the optional copy is omitted.

**Earliest coverage.** The new complete roster history can start with the first eligible Sort opening after an approved cutover, once that Sort is sealed. The report can show the earliest retained linked mark and earliest sealed roster date for its scope. There is no verified complete production date. Older linked marks may be recoverable from the surviving sources. Missing statuses and rosters remain unavailable.

## Retention and estimated storage for approval

Recommend **365 days** for sealed rosters and status-only attendance outcomes, then a bounded purge for these new records only. Retain roster input changes needed for the recovery window plus an independently verified predecessor state for each entity, so pruning older revisions cannot break later seals. A checkpoint and purge implementation should follow approval. This change installs no purge for the new tables and changes no source retention periods. Keep live collection disabled until the retention policy and production cutover are approved.

Illustrative workload, without production measurement. At 400 distinct people per operating day and 260 operating days/year, 15% additional valid Combo placements produce about 120,000 placement rows. At up to one mark per placement that is another 120,000 outcome rows. At a planning allowance of 250–400 bytes per row including indexes, together they use roughly 57–92 MiB per year before index bloat and WAL. The journal is an incremental store. A 5,000-row seed and 100 changed source rows per week at 250–400 bytes per revision add about 2.4–3.9 MiB in the first year. Measure heap, indexes, journal growth, transaction lock duration and WAL in staging using representative names and work-area paths before approving an operational budget.

## Migration and rollout for approval

1. Have the owner approve what counts as the close roster, the 365-day policy, and whether to retain surviving timecard marks. Keep `NEOSTAFFING_HISTORY_ENABLED` off until the rest of the release checklist is met. Ordinary model bootstrap can create empty additive tables. It does not seed or install the journal triggers.
2. Verify the exact release on isolated PostgreSQL, confirm source-table ownership and schema search path, and plan cutover outside a Sort. The explicit command is `python scripts/initialize_staffing_reporting_history.py --confirm`, with a deliberately selected PostgreSQL `DATABASE_URL`. Add `--retain-existing-timecard-marks` only for the approved historical status copy. Installation, seed and optional copy share a transaction. The initialization locks only the three roster source tables with a five-second lock timeout. An already-seeded database remains idempotent. Review rollback in staging before running it with production credentials.
3. Enable the feature before the first intended Sort opens and compare sealed placements to the canonical close roster during a staging and then approved live observation window. Confirm original area after later transfers, counts across Combo placements, false-empty coverage and stale corrections. Confirm the existing scheduler and source cleanup still operate within their normal budgets.
4. To suspend the new report and scheduled writer, disable the feature flag. The explicitly installed source journal still records staffing mutations until a DBA removes or disables its three named triggers. Retain all captured rows. If the journal is interrupted, treat the gap as unavailable and require a fresh verified baseline before a later reactivation. Do not create rosters for dates before the baseline.
